## 0. FINAL DESIGN (2026-11-26, supersedes 3.3, the cohort / kill-switch paragraphs of 3.4 and the experiment parts of 1, 3.5, 3.7, 3.8 and 5)
The user rejected the first backend (3 new tables, HTET-only, A/B split). Final product rules, all implemented in BE branch `phase-132-free-test-credits`:
1. **No new tables.** The counter is ONE new column, `u_exam_enrollments.free_test_credits_used` (unsigned smallint, NOT NULL, default 0). It sits on the canonical enrolment row of the (user, `group_code`) (oldest non-dropped row), so all papers of one course share one budget.
2. **Every exam, same limit**: `config('free_credits.limit')` = env `FREE_CREDITS_LIMIT`, default 5. No per-exam config, no rollout date.
3. **Everyone gets fresh credits at go-live**, including users already in free trial / trial_end. Default 0 = fresh 5. Old attempts are not counted, no backfill.
4. **Status rule.** `EnrollmentAccessService::hasPaidAccess` true (status `active` and inside valid_till + grace) = unlimited: never counted, locked or shown a chip (`enabled:false`). Every other state (trial, trial_end, expired, active-but-lapsed) = the limit applies. When a paid course lapses the limit applies again with whatever the counter was (never reset).
5. **What costs a credit**: sectional, chapter, full-length (the `createExam` path), 1 each, taken when the attempt row is created, inside the `createExam` transaction. Topic Test and the Practice Test never count. Daily: attempt #1 of today's test is free and not counted; a retake costs 1 credit (as before) and is NEVER refundable. There is no separate "first test free" any more (`first_test_free_available` is always false, field kept for the dashboard).
6. **No A/B split.** Switches: env `FREE_CREDITS_ENABLED` (default false) AND one GrowthBook boolean feature (`FREE_CREDITS_GROWTHBOOK_FEATURE`, default `free-test-credits-enabled`), evaluated server side by `GrowthBookEvaluator::isOn` (same public SDK payload, cached 5 min). Fail-safe = OFF (payload unreachable, feature missing or not true = today's legacy rules). The API keeps `variant: "treatment"` when enabled so the dashboard (`enabled === true && variant === "treatment"`) needs no change. Dropped: variant_source, forced variants, sticky assignment, rollout_at, log_only, server-side `$exposure` event (the enum case stays, nothing sends it). This is a kill switch, not an experiment, consistent with DEVELOPMENT_RULES 10A.4(c): the backend decides access.
7. **Atomic**: `UPDATE u_exam_enrollments SET free_test_credits_used = free_test_credits_used + 1 WHERE id = ? AND free_test_credits_used < limit`; 0 affected rows = locked (403 `free_credits_exhausted`, nothing created). It runs in the same transaction as the attempt insert, so a later failure rolls the credit back and two taps / two devices can never pass the limit.
8. **Held tests (re-open is free).** A test that already has an unsubmitted attempt (`exam_attempts.status` started / in_progress, same user, course, type, test_id) is "held": starting it again never costs and is never blocked. The new attempt is created and the older unsubmitted attempts of that test are retired to `expired`, so a test is held by one attempt only (no chain of free retakes). A retake after submit costs again. `held_tests` in the status API is derived from these rows.
9. **Refund without a ledger (decision).** The charge is recorded on the attempt itself: `exam_attempts.result` JSON gets `{"free_credit":{"charged":true}}` when it is created (and is carried to the new attempt on a free re-open). `ExamAttempt::getResultAttribute` hides the `free_credit` key from every reader (lists, `getExam`, API resources), so the existing `result` consumers see no change; the service reads it with `getRawOriginal`. `POST /v2/free-credits/abandon` refunds only when, under a row lock on the attempt: status is started/in_progress, it carries `charged`, `created_at` is inside `FREE_CREDITS_REFUND_WINDOW_SECONDS` (120), no `exam_attempt_questions.user_option` is recorded, and refunded attempts of the course are below `FREE_CREDITS_MAX_REFUNDS` (3, counted from the `refunded_at` stamps, no table). The refund decrements the counter (`> 0` guard) and flips the attempt to the EXISTING status `expired` with `refunded_at` stamped, in one transaction. Why this closes the exploits: idempotency = a refunded attempt is no longer open, so a second call finds nothing (answers `already_refunded`); refund-then-resume = an `expired` attempt cannot be answered (`assertExamMutable`), heartbeat reports expired, `exam-attempts-list` only lists in_progress / submitted, and starting the test again is a normal charged start; an attempt made while paid has no marker so it can never farm a credit. Always 200 `{refunded, reason}`, 404 for another user's attempt, daily attempts answer `not_refundable`.
10. **Reduced behaviour (documented, accepted).** The lazy stale sweep (refund of an attempt abandoned by a killed WebView) is dropped: it needed the ledger's per-row state. The student loses nothing for that test because a held test re-opens free; only a never-reopened abandoned attempt keeps its credit. The per-account `locked_count` / `last_locked_test_type` columns are gone, so `Payment Completed` now carries `credits_used` and `free_credits_variant: "treatment"` (from the counter) but no `test_type`. A daily start that fails while building questions leaves the attempt in_progress and the next start resumes it without a second charge, so no compensating refund is needed.
11. **API contract unchanged** (see 3.5 and the dashboard branch): `GET /api/v2/free-credits?course=|exam=`, 403 `free_credits_exhausted` body, `POST /api/v2/free-credits/abandon`, list `locked` + `credit_cost: 1`.

## 1. Problem / objective
Unpaid HTET users take ~9 tests in 12 days, open checkout ~11 times and tap "Continue Free" (ticket CC-196). Today the "paywall" is soft: only the first test of every chapter / section / paper is free, and everything else is locked, but the unpaid count is still high because there are many chapters, plus daily tests, the Topic Test and the first Practice Test. Goal: one server-enforced rule, **5 free test credits per exam**, daily test free once per day, first test free, paid never locked; HTET only, as a 50/50 experiment on NEW HTET users (HTET exam is 26-27 Dec 2026), flag OFF = today's behaviour byte for byte. Success metric: 14-day paid conversion of new HTET users; guardrails day-7 retention, daily-test participation, checkout-to-payment capture.

## 2. Scope
- **In:** BE credit service + ledger + per-exam config + deterministic 50/50 cohort; gate in every credited test-start path (test series: sectional / chapter / full-length via `create-exam`; daily test; see 3.2 for the rest); credits status API; lock response shape; dashboard UI (credit counter on cards + dashboard, soft banner at 3 used, lock screen, hide "Continue Free" when locked); tracking (`Test Locked`, fix `Payment Paywall Rendered`, `test_type` + `credits_used` on `Purchase Intent Initiated` / `Payment Completed`, `source=cutoff_meter`, user property `free_credits_remaining`); en/hi/mr copy; tests.
- **Out (not doing):** pricing changes or a new Rs 149 product (see ambiguity A1), GrowthBook (not used for this, see 3.4), any change for CTET / other exams, RN native work, paid-user behaviour, result/report gating (unchanged), the public guest "weekly test" (`/v2/practice-test`, no enrolment, guests allowed), the unauthenticated `POST /v2/sectional-tests/generate*` routes (flagged in section 6, not part of this).

### 3.3 Data model (BE, additive migrations, reversible `down()`, run only own file locally)
1. `exam_free_credit_configs` (one row per exam; absent row = off): `exam_id` unique, `enabled` bool default false, `credit_limit` tinyint default 5, `rollout_at` timestamp (new-user cutoff and "credits counted from"), `treatment_pct` tinyint default 100 (HTET = 50), `salt` varchar, `max_refunds` tinyint default 3, `refund_window_sec` smallint default 120, timestamps. Matches the ticket's `free_test_credits_enabled` / `free_test_credits_limit`. Chosen over `exams.metadata` / `settings` because it is explicit, indexable, cacheable (`Cache::remember` 60 s, so the kill switch bites within a minute), and the owner already applies prod schema/SQL by hand. Env master kill `FREE_CREDITS_ENABLED` (default false) in `config/free_credits.php`.
2. `free_credit_accounts`: `user_id`, `exam_id`, unique `(user_id, exam_id)`, `cohort` enum(`treatment`,`control`,`excluded`), `rollout_at` snapshot, `credit_limit` snapshot (nullable = use config), `refunds_used`, `last_locked_at`, `last_locked_test_type`, `locked_count`, timestamps. The row is the `SELECT ... FOR UPDATE` target for concurrency and the cohort record.
3. `free_credit_events` (ledger): `uuid`, `account_id`, `user_id`, `exam_id`, `kind` enum(`free_first`,`free_daily`,`credit`), `test_type` (`daily_test`,`sectional`,`chapter`,`full_length`), `test_ref` (test id, for A7), `source_type` (`exam_attempt` / `daily_test_attempt`), `source_id`, `status` enum(`held`,`settled`,`refunded`), `started_at`, `refunded_at`, `refund_reason`. Unique `(source_type, source_id)` = idempotency; index `(account_id, status, kind)`. `credits_used = count(kind='credit' and status<>'refunded')`; remaining = `limit - credits_used`. Counters are derived, never stored (no drift).
Never edit stale `* copy.php` files; models `FreeCreditAccount`, `FreeCreditEvent`, `ExamFreeCreditConfig` with `HasUuid` where public.

### 3.4 Enforcement (ONE service, called from every start path)
`App\Services\Access\FreeTestCreditService` (next to `ContentAccessService`):
- `decide(User, UExamEnrollment $enrollment, string $testType, ?int $testRef, ?Carbon $now): Decision` -> `Legacy` (flag off / not eligible / control / paid: caller keeps today's code path untouched), `Allow(kind)`, or `Lock(meta)`.
- `record(Decision, $attempt)` writes the ledger row INSIDE the caller's transaction (createExam already has `DB::transaction` + enrolment `lockForUpdate`; daily `resolveAttempt` has its own transaction on the latest attempt). Locking order: enrolment row, then the credit account row, never the reverse.
- `settleStale(account)` the lazy refund sweep (A6), called by `decide` and by the status endpoint.
- `status(User, enrollment): array` for UI (3.5).
Call sites: `ExamController::createExam` (replaces the `isFreeTest` check when `decide` returns non-Legacy; legacy path otherwise), `DailyTestController::start`. Test lists (`FullLengthExam::getTestsList`, chapter + sectional list) set `locked`/`credit_cost` from `status()` for credit-mode users so cards and server agree. Never trust the client for paid/credit state.
Why not middleware: the decision needs the resolved enrolment, the test target and a transaction; a middleware cannot hold the lock.
Why not GrowthBook / Amplitude for the split: both bucket in the browser, the server must enforce, DEVELOPMENT_RULES 10A.4(c) forbids experiments on access/entitlement, and a client-only gate is bypassable by calling the endpoint.
**Cohort:** at first `decide`/status for an eligible user: `eligible = config.enabled && enrolment.created_at >= config.rollout_at && never paid`; `cohort = crc32(salt|user_uuid) % 100 < treatment_pct ? treatment : control`, saved on the account (sticky, survives limit changes). Not eligible -> `excluded`. Control/excluded = Legacy path, no ledger rows. Exposure analytics: on account creation send `$identify` with user property `free_credits_group` = treatment|control (server-side, once, by assignment time so the denominator is the assigned set, not page views).
**Kill switch / ramp:** `enabled=false` or env off -> Legacy for everyone immediately (ledger kept). Ramp = raise `treatment_pct` (existing assigned users keep their cohort; new ones hash against the new pct only if you also want to re-bucket control users: do NOT, ramps only add NEW users). Flag off = zero queries beyond one cached config read.

### 3.5 API changes (BE + TS types in `lib/api/*`, shipped together)
- `GET /v2/free-credits/{course}` -> `{ enabled, cohort, limit, used, remaining, daily_free_available, first_free_available, banner: none|soft, locked, release_window_sec }` (`enabled:false` for Legacy users: UI renders nothing, exactly today's screens). Throttle 60/min. Used by cards, dashboard widget, banner. Cached client-side 60 s, invalidated after start / release / payment.
- Test lists add per-test `credit_cost` (0 or 1) and `locked` derived from credits.
- Lock error (exam + daily start): HTTP 403, `{ status:false, message, error_code:'free_credits_exhausted', data:{ used, limit, remaining:0, test_type, meter:{gap, pass_mark}|null, checkout:{plan:'1month-onetime', source:'cutoff_meter'} } }`. Same envelope as `renewal_required` (`ApiResponse::forbidden`), so unknown clients (old RN WebView cache) still fall into the existing paywall path.
- `POST /v2/free-credits/release` `{ attempt_type, attempt_id }` (own attempt only, 404 otherwise, idempotent).
- Server events: `Test Locked` is sent by the CLIENT when it shows the lock screen (one place, has the screen `source`); the server records `last_locked_*` on the account so `Payment Completed` can add `test_type` and `credits_used` without trusting browser input.

## 6. Blockers / risks
- ⚠️ Payments/revenue: wrong lock = lost learners the week of the exam. Mitigation: log-only soak, kill switch (`enabled=0`, cached 60 s), control group untouched.
- ⚠️ Time: 16.5 dev-days vs ~31 days to the exam including the 2-week read-out.
- Concurrency: credit write must share the caller's transaction and lock order (enrolment -> account); a deadlock on `createExam` would be a revenue-path outage. Unique index is the backstop.
- Daily `start` builds questions after the attempt row: a 5xx after the credit was taken burns a credit; the lazy sweep refunds it (idle, <2 min, no answers).
- Test lists compute `locked` separately from `createExam`: they must call the same `status()` or the card and the server disagree (known drift class in this repo).
- Flagged, not fixed: backend trusts browser prices (DEVELOPMENT_RULES 10), so the "preselected pack" is a UI default only; `POST /v2/sectional-tests/generate*` has `auth:sanctum` commented out (cannot be credited; confirm unused: **Not verified** that no client calls it); `CUTOFF_METER_ENABLED` prod state unknown.
- `main` push auto-deploys BE + dashboard; Atlassian connector used here is on the deprecated v1 endpoint (tell the user to re-add the connector).
