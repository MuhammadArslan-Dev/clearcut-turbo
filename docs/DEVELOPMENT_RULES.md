## 0. Task Workflow (mandatory order)

1. **Read this file.**
2. **Analyze existing code for the task** — find the closest existing page/component/hook/endpoint (`Grep`/`Glob`) before writing anything.
3. **Reuse.** Check the component catalog (section 3). Use it as-is → else extend it (new prop/variant) → else create a new reusable component that follows the design system.
4. **Compare any provided design/screenshot with the existing design system** and adapt the design to existing components/tokens. Do not copy the mock pixel-for-pixel with new colours, radii or fonts.
5. **Implement** following sections 2–7.
6. **Verify** (section 8) — tsc, eslint, `check:colors`, and a real screenshot for UI work. Then the **break-it pass** (section 8.1): try to break your own change the way the client would, before saying done.
7. **Update this file** if a new pattern/component/gotcha was introduced.

Hard "don'ts":
- Don't create a component when an existing one can be reused or extended.
- Don't introduce random colours, spacing, font sizes, radii, shadows or new UI patterns.
- Don't redesign things the user did not ask to change (e.g. `MyCourseCard`: only its header was redesigned, at the user's request in phase 98; the buttons block is still client-approved and untouched).
- Don't add features the user didn't ask for (e.g. an extra "Next" button). Restyle only what's requested.
- Don't add a `Co-Authored-By: Claude` trailer to git commits (user preference). Commit/push only when asked.
- Don't create project copies, clones, worktrees or backup folders; one dedicated branch per task inside the canonical repo, merged into `main` only after verification and the user's go-ahead (full rule: root `CLAUDE.md` → "Git Workflow").

## 2. Frontend Rules (apps/dashboard focus)

### 2.1 Folder conventions
- Routes: `src/app/[locale]/(protected)/...` (`(exam)` group = full-screen attempt experience, no dashboard shell).
- Feature code: `src/components/features/<feature>/` (components + `hooks/` + `constants.ts`).
- Shared primitives: `@clearcut/ui/*` first, then `src/components/ui/*` (dashboard-local), then `src/components/layout/*`.
- API functions: `src/lib/api/<domain>.ts`. Types live beside the functions.
- Navigation: always `import { Link, useRouter } from "@/i18n/navigation"` (locale-aware), never `next/link`/`next/navigation` router for app routes (`useParams`/`usePathname` from next/navigation are fine).
- **Blog page titles ≤ 60 characters and meta descriptions ≤ 160, as shown in search results** (`apps/blog/src/lib/seo/seo-text.ts`, 2026-10-21). Build every title with `seoTitle([variants…], tail)`: variants most keyword-rich first, the first that fits wins, " | Clear Cutoff" is added only when there is room (else `{ absolute }`), the page tail (" – Page N") is never cut. Descriptions go through `seoDescription()` (`generateLocaleMetadata` applies it). Question-bank titles come from `questionBankSeo()` (`components/question-bank/pages/page-copy.ts`) with the variant keys in `QuestionBankPage` (en + hi); keywords chosen from a 2026-10-21 competitor/volume check: "Question Paper", "PYQ", "MCQ", "with Answers", CDP/EVS short names (`subjectShort`), PRT/TGT/PGT in capitals (`levelLabel`, never `unFormatSlug(level_id)`). Guarded by `lib/seo/seo-text.test.ts`. One `<h1>` per page: a second `CustomizableHeader` takes `as="h2"`.
- Internal links are always `Link` from `@/i18n/navigation` — never a plain `<a href>` and never an `onClick` + `router.push` (search engines don't run click handlers). Plain `<a>` only for external URLs (share/WhatsApp, attachments), `#anchor` jumps, and the question-bank pagination/chapter links (heavy pages: with `prefetch={false}` a `Link` click shows nothing until the payload arrives, with prefetch on it downloads several pages up front — see section 10). Pass `Link` an **unprefixed** path and **no `locale` prop**: it adds `/hi` itself, and an explicit `locale` makes it emit `/en/...` (a redirect hop) on English pages.

### 2.2 Data fetching
- Use `apiFetch` (`lib/api/client.ts`). Base URL is `NEXT_PUBLIC_LARAVEL_MAIN_BACKEND` and **includes `/api`**.
- Server state → **TanStack Query** hooks in `features/<feature>/hooks/` with explicit `queryKey` constants, `staleTime`/`gcTime`, and `invalidateQueries` after mutations (see `useDailyTestHistory`). Never refetch-on-mount with a skeleton flash for data that is already cached.
- Client-only UI state → Zustand store in `src/store/*`.
- **Public URL ids are UUIDs / opaque codes, never numeric DB ids.** API function signatures are id-scoped (`getDailyTestHistory(courseId)`, `startDailyTest(courseId, testId)`).
- The `courseId` in URLs is the **enrollment uuid**. Resolve to the exam via `useEnrollmentForCourse(courseId)` (matches by `uuid`), not by exam id.
- **A "Retry" button must `cancelQueries` before it refetches** (2026-10-27, CC-152). `refetch()` / `refetchQueries()` does **nothing** while a query is still fetching with `data === undefined` — react-query's `Query.fetch()` only cancels-and-refetches when `data !== undefined`, and otherwise returns the in-flight promise, so `cancelRefetch` (true by default) never applies on a first load. That is exactly the state a retry button is shown in, so the button silently sends no request. `await queryClient.cancelQueries({ queryKey })` first, then `refetchQueries`. `useSlowLoad` takes query **keys** rather than a `refetch` callback for this reason — keep it that way so no call site can reintroduce the bug. Caught only by asserting the request count in Playwright; a click test alone looks like it passes.

### 2.3 Performance rules (exam/attempt screens)
- Per-second things (timers) live in isolated leaf components (`LiveTimeLeft`, `ElapsedClock`), never in a parent that re-renders the question tree.
- Use selector-based Zustand subscriptions (`useExamStore((s) => s.x)`); never subscribe to the whole store.
- Per-question timers use refs, not state.

### 2.4 i18n (en / hi / mr) — required for every user-visible string
- No hard-coded UI text. Use `useTranslations("<Namespace>")`.
- Add keys to **all three**: `messages/en`, `messages/hi`, `messages/mr` — **in `apps/dashboard`**. The locale set is per app: `apps/blog` and `apps/landing` ship **en + hi only** (`messages/{en,hi}.json`, no `mr`), and `apps/tools` has no `next-intl` at all. Check which files the app actually has before adding a third.
- **Edit message JSON by appending, not by re-serialising.** Writing the whole file back out (e.g. `json.dump`) normalises indentation and drops the blank lines between sections, which turns a 25-key addition into a ~77-line diff that nobody can review. Splice the new namespace in ahead of the closing brace, then re-parse and assert every pre-existing key is byte-identical.
- New namespace file (`messages/{locale}/<name>.json`) **must be registered in the `load()` list in `src/i18n/request.ts`** — the namespace key can differ from the filename (`dailyTests.json` → `DailyTests`, `dashboardHome.json` → `DashboardHome`, `onboarding` → `Onboarding`).
- Dates/numbers: use `Intl` with the locale map (`en-GB`/`en-US`, `hi-IN`, `mr-IN`), never English month names.
- Verify by switching language in the UI (hi/mr) — text must not overflow layouts.

### 2.5 Analytics
- Dashboard uses Amplitude via `lib/analytics/*`; event names/payloads are typed in `types.ts` + `events/*`. `ANALYTICS_EVENT_CATALOG.ts` is documentation only — never import it.
- Practice Test and Daily Test reuse the test-series events (`Test Started` / `Test Submitted` / `Test Abandoned`) through the `trackLite*` helpers in `lib/analytics/testFunnel.ts`, with `test_type` = `practice_test` / `daily_test`. Never add event names for a new kind of test; add a `test_type` value.
- **A/B tests and feature flags: read §10A (GrowthBook) before touching any experiment.** Variant assignment = GrowthBook via `@clearcut/experiments`; results = Amplitude (`$exposure` + user property `exp_<flag_key>`), no new events.

### 3.3 Reuse decision ladder
1. Exists and fits → use as-is.
2. Exists but lacks a prop → **extend** it (optional prop, default = old behaviour, so other screens don't change). Verify all callers.
3. Nothing fits → create a new component in the right layer (shared if ≥2 apps/features could use it, else the feature folder), built from `Card`/`Text`/`Button`/tokens, with i18n strings passed in/`useTranslations`.
4. Small one-off layout helper used by a single file (e.g. `Stat` in `DailyTestHistoryRow`) may stay local.

## 4. Design System Rules

- **Colours: tokens only.** Source: `packages/design-tokens/tokens.css` (+ dashboard `src/styles/tokens.css`). Families: `--color-brand`, `--color-primary-bg-soft`, `--color-success-bg-soft`, `--color-danger`, `--icon-positive-*`, `--icon-negative-*`, `--icon-notice-*`, `--background-gray-subtle`, `--color-surface-gray-*`. Use via Tailwind (`text-brand`, `text-surface-gray-muted`) or `var(--…)`.
- **Never** write hex/rgb/hsl/oklch literals or `bg-[#…]` — `pnpm check:colors` fails CI (per-package baseline can only go down). Need a new colour → add a token, not a literal.
- Tokens can resolve differently per app (`--color-brand-dark`: dashboard `#0053a2`, blog shadows with `#006bd1`). Check the app's own CSS.
- **Typography:** `heading-*`, `body-*` classes / `Text` variants. Emphasis via `!font-bold|semibold`. No arbitrary `text-[13px]`.
- **Spacing/layout:** Tailwind scale (`gap-3|4`, `p-4 md:p-6`). Page container: `mx-auto max-w-[1200px] p-4 md:p-6`. Radii used: cards 12px, pills fully rounded, nav elements per existing components.
- **Breakpoints** (dashboard `globals.css`): xs 500, sm 640, md 768, 2md 900, lg 1024, 1lg 1150, tablet 800. Mobile-first; verify at ~390px and ~1440px.
- **z-index/shadows:** use `--z-*` / shadow tokens; don't merge tokens across apps.
- **Tailwind v4 `@source`:** a shared package emitting utility classes must be listed in each consuming app's `globals.css` (`@source "../../../../packages/X/src/**/*.{ts,tsx}";`) or its classes silently don't generate.
- Consistency: same screen type ⇒ same header/card/tab/pagination look everywhere (see Daily Tests list ↔ history ↔ result).

## 5. Shared-package Rules
- No barrel files; add exports via the package's `exports` map (`"./name": "./src/name.ts"`).
- `createPersistedStore` always uses `skipHydration: true`; hydrate via `useHydrateStore` in a mounted client component. Don't bypass.
- New package → extend `tsconfig.base.json`.
- Cross-cutting change → check whether dashboard needs the same change separately.
- **Shared-package behaviour changes must be additive.** `@clearcut/auth` gained `onAuthenticated` (stay on the page after login) and `LoginCopy` (per-mount copy override) as *optional* inputs whose absence leaves blog/landing byte-for-byte on the old path — verify by running landing's login (`/dashboard?token=` redirect + original copy) after touching it. See root `CLAUDE.md` "Tools: Save for Future".

## 6. Backend Rules (Laravel 12)

- **Layering:** Route (`routes/Apis/V2/*.php`, registered from `routes/api.php`, `auth:sanctum`) → Controller (`app/Http/Controllers/API/V2`) → Service → Repository (interface bound in `AppServiceProvider`) → Resource. Keep controllers thin; business logic in Services.
- **Responses:** always `App\Helpers\ApiResponse` → `{ status, message, data }`.
- **Models:** prefixes E* (exam), S* (subject), U* (user), Mapping*; use `HasUuid`. **Never edit stale `* copy.php` files.**
- **Public identifiers = UUIDs**; never expose numeric ids or internal ids in URLs/responses when a uuid exists.
- **Authorization (IDOR-safe):** resolve every nested resource through ownership chain and return **404 (not 403)** on any failure. Daily tests: enrollment(uuid, own, active) → assignment(user, exam, test) → attempt(user, test, uuid).
- **Validating maps keyed by user-visible names (e.g. `subjects`: `{ "E.V.S.": [...] }`):** never use `a.*.*.b` wildcard rules — Laravel's dot-notation expansion mis-parses keys containing `.` and silently drops them from `validated()`. Validate with a closure and rebuild the stored array from known keys.
- **MySQL `JSON` columns re-sort object keys (length, then bytes).** Never rely on key order of a stored JSON object — derive the order from its source of truth (e.g. the tracker's subject order comes from the live syllabus tree) or store a list.
- **Store ids, derive display data.** `user_syllabus_trackers` keeps only `exam_id` / `root_navigation_id` / `navigation_id` (NULL = unscoped, never a `0`/`"full-exam"` sentinel) plus the user's `progress`; names, logos, subjects and chapters come from the current syllabus via `SyllabusTreeService` and follow `?locale=en|hi|mr`. A NULL-able column inside a unique key needs a **VIRTUAL** generated column (`IFNULL(col,0)`) — MySQL forbids `ON DELETE CASCADE` on the base column of a **STORED** one.
- **Sanitize responses:** whitelist fields (e.g. `publicMeta`, sanitized `topic_meta`) — no raw model dumps.
- **Migrations:** new migration per change, reversible `down()`, never edit an already-run migration. Run locally, verify. **Locally, run and roll back ONLY your own file: `php artisan migrate --path=database/migrations/<file>.php` and `migrate:rollback --path=<same>`** (2026-11-12, phase 100). The local `clearcut` `migrations` table is behind the real schema (~13 old migrations show "Pending" although their tables exist), so a bare `migrate` applies unrelated old migrations and then dies on an existing table, and a bare `rollback --step=1` then rolls back *someone else's* migration (it dropped `daily_tests.uuid`; restored the same day by rolling the two stray migrations back). Check `--pretend` first.
- **Question explanations (phase 100):** text lives per locale in `question_trans` — `explanation` = correct explanation (BigQuery `correct_option_explanation`, legacy `explanation`), `incorrect_explanation` = BigQuery `incorrect_option_explanation`, NULL = none. Row mapping is in ONE place, `App\Services\Questions\QuestionSyncRecordService` (queued `SyncQuestionsJobNew` and `php artisan questions:sync-exam` both use it): a blank value never overwrites a stored one, ids/sheet errors (`C_0454`, `#VALUE!`) are rejected. Any response that returns `explanation` must return `incorrect_explanation` beside it. The legacy flat `questions` table (MiniTest, `Tests\QuestionResource`) has no incorrect column.
- **Data:** DB timezone +05:30. Daily-test questions come from `question_new` (`QuestionNew` + `QuestionTrans`).
- **Style:** Laravel Pint (`vendor/bin/pint --dirty`). Heavy work → queued jobs. Errors → Sentry.
- **Tests/fixtures:** create temporary users/tokens/rows for manual verification on the **local** DB only, and remove what you created in shared tables. The Playwright fixture user and its `pw-` token stay in place (the user keeps using that session) unless asked to delete them; say in the report what was left behind. Never write test rows to a remote/shared DB. Prefer `tinker --execute` (interactive tinker hangs).
- Frontend + backend contract changes must ship together; update TS types in `lib/api/*` when a response shape changes.
- **Scoring (phase 103): every test is scored by `App\Services\Scoring\ScoringService`, nowhere else.** Marks per answer come from the question's own `e_instances.marking_scheme` → `exams.marking_schema` → documented default `{1,0,0}`; a penalty only when that instance has `negative_marking`; the correct option is the attempt language's (else the first valid key); cutoff = paper pass share (`pass_marks.general ÷ total_marks`, else `metadata.cutoff`) × this test's max marks, and **no documented pass mark = no cutoff**. Submits return its `scoring` block (dashboard type `TestScoring`, `lib/api/scoring.ts`). Never compare `correct_option` inline, never hardcode a pass share, and never let the result screen invent a cutoff (`TestResult` shows none when `cutoff` is null).

### 8.1 Break-it pass — think like the client (every feature, bug fix and code change)

The team's tickets come from evidence (Clarity dead/rage taps, Sentry, Amplitude, SQL) and end in a measurable "Done when". A screen that looks right and survives one happy-path click is **not done**. Before reporting, try to break your own change from the angles below (only the rows that apply), and put the result — including what you did NOT verify — in the phase file's §8.

**Baseline first.** Measure the symptom on the OLD code (CLS, request count, dead taps, the failing request) before changing it, so "after" means something; record both numbers. (CC-175 shipped without an old-code CLS baseline.)

| Angle | Probe | Passes when |
|---|---|---|
| Dead taps | At 390px tap every CTA in its empty / disabled / loading state; `document.elementFromPoint` at the tap spot (an overlay on top?); grep new `cursor-pointer` without a handler | Something visible happens (hint, navigation) — never nothing |
| Retry / refresh | Hang the request, then fail it, then click Retry | Exactly **+1 request**; a late old response cannot overwrite a newer state (§2.2) |
| Double tap | Tap twice fast; tap immediately after a transition / animation | Exactly 1 POST / navigation; the second tap is not eaten by a stale closure (§10) |
| Network failure | Dropped request, 500, 4xx, 403, malformed JSON, hung 40 s, failing twice in a row | Message + retry + a way out; a 4xx is never auto-retried; a network blip is a breadcrumb, a real failure goes to Sentry |
| Layout | CLS via `PerformanceObserver` at 390px (4x CPU for speed work) on a free port; toggling a control must not resize its row; a hint, error or message that appears must not move the control under the finger (measure the button's `top` before/after the tap — CC-90's first version pushed Continue 26px down) | Before/after numbers recorded; CLS < 0.1; the control stays put |
| Language / device | en + hi + mr; 390px + desktop; FB/IG user agent and Slow 4G where the flow is hit from ads | No hard-coded English, no overflow, no dependence on a popup the in-app browser blocks |
| Numbers / data | Compare the screen with the DB for a real user; boundary and empty values: 0, 1, max, null, soft-deleted rows | Totals reconcile; no `NaN`, placeholder or stale value |
| Analytics / tracking | Capture the outgoing events with the ingestion hosts blocked; reuse existing events (§2.5); unload events in a fresh browser context | Right name, once per attempt, right properties, conversion tracking untouched |
| Backend / API | A second user's token → 404; invalid, missing and oversized input; duplicate request or webhook (idempotency); two requests at once; migration up AND down; for performance work the response JSON before/after must be identical | No data change, no 500, no leak of another user's data |
| Regression | What else shares this component, endpoint, store or shared package? Open those screens | Callers of a shared piece render unchanged (§5: additive only) |
| SEO / links | Internal links stay `Link` / `<a href>`; the content is still in the server HTML | No click-handler-only navigation |
| Feedback channel | The message you rely on actually renders (toast container mounted? error boundary?) | The user can see it. Example: no `ToastContainer` is mounted, so the existing `toast.*` calls show nothing |

**Test the test.** A probe that finds nothing must first be shown able to find something (positive control). Check the HTTP status of every probe: a 429 rate limit or a 503 once produced a false "none found". Separate local-environment drift (missing column, no Redis, a `.test` host answering 503 in the browser) from product bugs, and say which it was. A raw `tsc` count includes phantom `.next/types` errors — compare per file, before vs after. `window.resize` does not change the viewport in the Chrome tool: render the page in a same-origin `<iframe>` of the target width. When something needs a decision, stop that item and document the options (phases README rules 2–5).

**Keep this list alive.** When a user correction, a Sentry issue or a review finds a defect class or a missed check, add a row or sentence here (no new document), add a changelog line in §11, and if it is a user preference, a memory feedback note.

## 9. Environment Gotchas (Windows)
- **YOU start the dev server and set local env vars yourself; never ask the user to (2026-11-19).** Needs a local `.env` value (public/test keys only, `.env` is git-ignored)? Add it. Needs the server for a browser check? Start it with the Bash tool in the background (`run_in_background`), check it answers, and stop it when done. If a server is already running on the port, reuse it. This overrides the older "no background jobs" note for dev servers.
- Dev server: dashboard on port 3020 (`next dev -p 3020`, `NODE_OPTIONS=--max-old-space-size=4096` if low on memory / Jest-worker 500s). Don't start a second one; stop before restarting.
- Renaming/moving folders fails with "Permission denied" while the dev server watches them → stop the server first, then `git mv`.
- `scrollIntoView` shifts overflow-hidden shells → scroll the container (`el.scrollTo`) instead.
- Multi-line scripted edits: write a script file (Python) instead of shell heredocs with quotes.
- **Never run several Playwright test agents at once, and never let each start its own dev server.** Three `next dev` copies + Chromium instances took free RAM to ~1 GB and Turbopack died with `0xc0000142` ("node process exited before we could connect"), leaving the user's own dev server returning 500 until it was killed and `.next/dev` cleared. Test against the one already-running server, one agent at a time, and remove temp app copies (`apps/_pwtest`, `apps/*-qa*`) afterwards — an orphan copy under `apps/` is also scanned by `check:colors` and fails CI-style runs with a bogus `+517`.
- **Bundle checks (CC-150):** `ANALYZE=true pnpm --filter dashboard exec next build --webpack` writes treemaps to `.next/analyze/` (the prod build is webpack, `cpus: 2`, ~2-3 min, ~2 GB RAM; it can run beside `next dev` because Next 16 keeps dev output in `.next/dev`). Measure on `next start`, not dev: Slow 4G + 4x CPU, cold cache, compressed bytes from Resource Timing. Delete `.next/types` afterwards - the production build generates page-props types that add ~18 phantom errors to `tsc`.
- **Dev-only code must not be statically imported in a layout.** `process.env.NODE_ENV === "development" && <X />` stops rendering but still ships the import (`agentation` cost every user 90 KB gzip). Use the module-level `DevAgentation` wrapper (landing, tools, dashboard, blog).
- A folder of pure components behind a barrel (`ui/icons`) needs `"sideEffects": false` in a package.json beside it, or every module in the barrel ships to every page.
- **Mini Test availability has ONE source:** `GET /v2/mini-test/count` (the topic's own questions, scoped to the enrolled course's exam) via `useMiniTestAvailability(topicId, courseId)`. The bottom bars, chapter header and the sidebar's `has_mini_test` (backend `PreparationService`, same exam scope) must all use it; never gate the button on a `limit=1` probe or an unscoped `withCount('questions')`. While the count loads the button's slot is reserved (invisible), 0/error hides it.
- Test tokens for local browser checks: mint with `php artisan tinker` (`createToken('pw-…')`) on the **local** backend only and pass it as `?token=` (or set `auth_token` in localStorage + cookie). Keep the fixture user's `pw-` token for the user's session, list it in the report, and delete it only when asked.
- Git Bash `/tmp` ≠ Windows temp; use the scratchpad dir for temp files.

## 10. Known Pitfalls (learned the hard way)
- Fixed-height `Card` overflow → `!h-auto !min-h-0`.
- Colour literal (`#000`) in a component fails CI → use a token.
- Course-card data: `get-course` resolves by enrollment uuid/group_code, not exam id; eager-loads may lack `name`.
- `language-modal` selected-state bug (uses route `locale` not `appLanguage`) is pre-existing.
- Image Resizer (`apps/tools`): JPEG size targeting lives in `src/lib/jpegBudget.ts` — aim at 98% of the max (never the min), keep the highest quality under the max, and check bytes against `KB × 1024` (not rounded KB). Switching document type must clear the image via `clearImageState()` and async work must check `workspaceVersionRef`. `apps/landing/src/components/pages/ResizeImageTool.tsx` is a separate copy of the same tool and still has the old one-way quality loop.
- Stray WIP files under `apps/dashboard/src/app/[locale]` (`page copy.tsx`, `test/`, `sentry-example-page/`) are not product surface.
- **Zustand selector must never construct a new object/array as its return value** (e.g. `useStore((s) => s.exam?.sections ?? [])`) — the `?? []` fallback (or any inline `{}`/`[]`/spread) is a fresh reference on every call, and zustand's `useSyncExternalStore`-based subscription treats "snapshot changed" as a reason to re-render, which re-runs the selector, which returns yet another new reference — an infinite loop (`Maximum update depth exceeded`), caught by the nearest error boundary as a blank/500 page with no other symptom. Select the stable field only (`useStore((s) => s.exam)`) and derive the fallback in the component body against a module-level constant (`const EMPTY: X[] = []; const sections = exam?.sections ?? EMPTY;`) — see `QuestionNavigatorSheet.tsx`.
- A `useMemo` keyed on a store sub-array (e.g. `[sections]`) won't recompute after a store action that **mutates a nested object in place** and only replaces the top-level object (`set({ exam: {...exam} })` — the exam store's `answer`/`toggleReview`/`clear` all do this). The array reference is unchanged even though its contents changed. Depend on the top-level object instead (or in addition): `useMemo(fn, [exam, sections])`.
- **`next/dynamic`-loaded modals whose content only fetches on mount have a chunk-then-fetch waterfall** — the data request doesn't start until the JS chunk has downloaded and the component has mounted, on top of the chunk download itself. `MyCoursesWrapTwo.tsx` lazy-loads several course/payment modals this way (deliberately, to keep the high-traffic Learn dashboard's initial bundle small — don't undo that). Fix by prefetching the query (`queryClient.prefetchQuery`, same `queryKey`/`queryFn`/`staleTime` the modal's own hook uses — export a small `prefetchX` helper next to the hook so they can't drift into two different cache entries) as soon as the id is known, not on click — see `useLevels.ts`'s `prefetchLevels` + `MyCoursesWrapTwo`'s `examIdsNeedingSelection` effect, which warms `BuySigleCourseModal`'s data ahead of time for any course still missing a paper/subject pick. The same gap likely applies to the other lazy modals in that file (`EditCourseModal`, the payment modals) if one of them turns out slow to open.

- **Error monitoring (404/500) — reuse `@clearcut/error-reporting`**, don't hand-roll: `redactUrl/redactSearch/scrubSensitiveData` in every `beforeSend`, `classifyNotFound` + `createPageErrorReporter` for not-found pages and error boundaries. Never `captureMessage` every 404 (noise) and never breadcrumb-only (invisible) — see root `CLAUDE.md` "Error tracking". A caught-and-returned error in an API route handler never reaches `onRequestError`: call `Sentry.captureException` in the catch.
- **`instrumentation.ts` belongs in `src/`** when the app dir is `src/app` (Next only scans the parent of the app dir; `instrumentation-client.ts` is found in either place). `global-error.tsx` must be at `app/global-error.tsx`, not under `[locale]/`.
- **`window.next.router.push()` to a route that doesn't exist falls back to a hard navigation** — a broken Link therefore usually shows up as a same-site-referrer 404, not an in-app one. `PerformanceNavigationTiming.name` stays the initially loaded URL after `pushState`, which is what `classifyNotFound` relies on.
- **Firefox for Android doesn't reliably support navigating a hidden iframe to a custom URL scheme** (`packages/auth/src/truecaller.ts`'s `useTruecallerAvailability`) — that iframe technique exists to dodge a *different*, Chrome-only problem (WhatsApp's Custom Tab replacing the whole page on a top-level scheme navigation), and silently doesn't work in Firefox, so the ambient "is Truecaller installed" probe always timed out `"unavailable"` there and then **permanently cached that wrong result for 180 days, cross-subdomain**, hiding the button on every later visit in any browser on that device. `isAndroidFirefox()`/`isTruecallerSupportedBrowser()` already correctly included Firefox — the bug was downstream, in a detection *mechanism* not being cross-browser safe, not in the platform check. Fixed by skipping the ambient probe entirely for Firefox (trust the platform check, rely on `useTruecallerLogin`'s existing reactive `APP_OPEN_GRACE_MS` fallback instead, same as an app-not-installed Chrome user already gets). General lesson: a browser-detection allowlist being correct doesn't mean every *technique* gated behind it works in every browser on that list — verify the actual mechanism, not just the UA check.
- **A `keepalive: true` fetch flushed on tab-hide/unmount can have its page torn down before `apiFetch`'s own catch block gets to wrap the failure** — the raw `TypeError: Failed to fetch` slips out un-wrapped instead of the usual `ApiError`, so an `isApiError(err) && err.isNetworkError` guard silently fails to match it (Sentry CLEARCUTOFF-NEXTJS-APP-2T, `useStreakTracker.ts`'s keepalive flush — reported as a bare TypeError with no `ApiError` in the chain). Use `isNetworkFailure(err)` (`lib/api/api-error.ts`) instead of that check anywhere a fire-and-forget write catches its own rejection — it matches both the wrapped and un-wrapped shape. Separately, `Sidebar.tsx`'s `setResumeState` background sync had no network-failure suppression at all (unlike `useStreakTracker.ts`, which already had the right idea for its own endpoint) — every retry-exhausted mobile network blip on `/preparation/:courseId` was reported as its own error, concentrated in Facebook/Instagram/Chrome-Mobile-WebView traffic (CLEARCUTOFF-NEXTJS-APP-74, 173 events/94 users). Both now route a non-actionable `isNetworkFailure` through `logger.breadcrumb` instead of `logger.error` — still visible as context on a later, unrelated error, not its own noisy issue; a genuine 4xx/5xx is still reported as an error either way.
- **Never put a long-lived auth token in a URL/deep link.** `apps/dashboard/src/components/ui/widgets/app-download/app-download-widget.tsx` (the "Continue in App" widget) used to embed the real Sanctum token directly in `clearcutoffapp://auth?token=<token>` — a URL can end up in browser history, referrer headers, or app logs, any of which would leak a permanent credential. Fixed by minting a short-lived (90s), single-use handoff code from the backend first (`createAppHandoffCode()`, `lib/api/authHandoff.ts` → `POST /v1/auth/handoff/create`) and putting *that* in the URL instead (`?code=`); the RN app exchanges it server-side for a real token (`POST /v1/auth/handoff/exchange`, see the RN repo's and backend repo's `CLAUDE.md` for the native/backend halves). If you ever need to hand off an authenticated web session to the native app again, mint a code — never pass the token itself, even "just this once."
- **`apps/dashboard/public/.well-known/assetlinks.json` had a wrong package name and an unfilled placeholder fingerprint** (`PASTE_YOUR_SHA256_HERE`) — meaning Android App Link (`autoVerify`) verification for `app.clearcutoff.in` could never have actually succeeded in production, despite the file existing and looking "configured." Fixed with the real package (`com.clearcutoff.app`) and the release keystore's real SHA256. A `.well-known` file existing is not the same as it being *correct* — always check the actual values, not just presence, when touching App Links/Digital Asset Links.
- **A `try`'s `finally` still runs after a `return` inside that `try`** — don't write a comment claiming a `finally`-driven reset (e.g. `setSubmitting(false)`) is "skipped" on some early-return path; it isn't, `finally` always runs. Caught this while adding a `return` after the success path in `BuySigleCourseModal.handlePurchase` — the comment was wrong, not the code; removed the comment rather than restructure around it.
- **A user-initiated submit (someone's actively waiting on it, e.g. "New Exam Added" purchase in `BuySigleCourseModal.handlePurchase`) needs different network-failure handling than a background sync** (contrast with `isNetworkFailure` → `logger.breadcrumb`-only above): still show the user a retry-able error message (there was none at all before — a failed purchase silently reset the button with zero feedback, Sentry CLEARCUTOFF-NEXTJS-APP-A7, another Instagram-in-app-browser network blip), but *also* still route it through `isNetworkFailure` so a non-actionable blip is a breadcrumb, not an error-level Sentry report, while a genuine 4xx/5xx stays error-level. Also worth checking for: a promise that *resolves* without throwing but without the expected `status: "success"` shape — that path was completely unhandled here too (no error shown, nothing reported) and needed the same treatment. New user-facing copy goes through `useTranslations`, all three locales (`messages/{en,hi,mr}/modals.json`), never hardcoded — even for a small addition.
- **Meta (Facebook) Pixel advanced-matching fields (`ct`/`st`/`zp`/`country`) only get auto-hashed and sent when set via `fbq('init', pixelId, {...})`, never inside a `track()` call's own custom-data object** — that's already documented at `packages/utils/src/meta-geo.ts` (`getMetaGeoData()`, IP-geolocated via `ipapi.co`, cached in `sessionStorage`) and `packages/auth/src/facebook-pixel.ts`, but the pattern wasn't reused everywhere: `apps/landing`'s only event (`PageView`, the highest-volume event platform-wide) never called `getMetaGeoData()` at all, and `apps/dashboard`'s `Purchase` (`useRazorpayPayment.ts`) / `CustomizeProduct` (`payment/initiated/page.tsx`) fired via the bare `trackFacebookEvent()` with no `init()` before them — `Purchase` especially, since it also fires from paywall modals (`MainPaywall`, `PreparationPaywall`, `full-course-payment-modal`) that never visit `/payment/initiated`, so there was no earlier page-level `init()` for it to inherit. Fixed by adding `trackFacebookEventWithUserData()` (`apps/dashboard/src/lib/analytics/facebook-pixel.ts`) — the one shared "init-then-track" helper, reused at every gap — and, for landing specifically, making the effect that awaits `getMetaGeoData()` the *sole* place `PageView` fires (the inline bootstrap script's own immediate `track('PageView')` was removed) rather than firing it twice. Don't add a new Meta event call site with a bare `fbq('track', ...)` — check whether it needs advanced matching, and if so use the shared helper, not a new copy of the init-then-track sequence.
- **`ipapi.co` (the free, unauthenticated geolocation API `getMetaGeoData()` depends on) returned an HTTP 403 Cloudflare bot-challenge page when checked from this dev environment** — reproduced both via a real browser `fetch()` and a plain `curl` with a realistic User-Agent, so not a User-Agent-sniffing issue. `getMetaGeoData()`'s existing try/catch already degrades gracefully (falls back to `{ country: 'in' }` only, doesn't break the event), so this doesn't crash anything, but it means city/state/zip can go silently missing even with the wiring now fixed everywhere, if `ipapi.co` is blocking the request. Unconfirmed whether this affects real end-user browsers/IPs the same way it did this dev environment's IP — flagged, not fixed, since swapping geolocation providers (or moving to server-side geo, e.g. Cloudflare's `request.cf.city`/`region`/`postalCode` if these apps sit behind Cloudflare) is a bigger infra decision than this fix's scope.
- **`apiFetch`'s final `return res.json() as Promise<T>` (`lib/api/client.ts`) was never wrapped in try/catch** — the only unhandled step in an otherwise fully-wrapped function. A body-read failure *after* headers/status already arrived OK (connection dropped mid-stream — an in-app browser backgrounding the tab mid-response is the common real case) skipped all of `apiFetch`'s own `ApiError` wrapping and reached the caller as a raw TypeError, with none of the endpoint/status/breadcrumb context every other failure path gets (Sentry CLEARCUTOFF-NEXTJS-APP-A9). Now wrapped the same way the `fetchWithRetry` catch above it already is — but `isNetworkError` is only set when the underlying `cause` is a `TypeError`; a `SyntaxError` from `JSON.parse` (the backend actually sent malformed JSON — a real bug) stays a full error rather than getting miscategorized as a network blip and suppressed by `isNetworkFailure` downstream. If you ever add another step after `res.ok` is confirmed true, wrap it too — "we already checked `res.ok`" doesn't mean nothing else in that step can fail.
- **`isNetworkFailure()`'s regex (`/fetch/i`) only matched Chrome/Firefox's network-error phrasing, not Safari/WebKt's** — Safari says "Load failed" for the exact same condition (CLEARCUTOFF-NEXTJS-APP-A9, iOS Instagram in-app browser), which contains neither "fetch" nor anything the old pattern caught. ## 10A. A/B Experiments & Feature Flags — GrowthBook (CC-192, phases 118 + 119)

> Read this whole section before adding, changing or touching an experiment. Everything here is what is actually in the code (`packages/experiments`, `apps/dashboard/src/lib/experiments.ts`, `ExperimentsPayload`, the webhook route, phase 119's Practice Test flag). Full history, measured numbers and open items: `docs/phases/118-cc192-growthbook-experiments.md`, `docs/phases/119-practice-prompt-skip-experiment.md`. If code and this section disagree, the code wins: fix this section.

### 10A.1 Why GrowthBook, and what each tool does
- **Goal (CC-192):** run A/B tests on the landing pages and the logged-in app repeatedly, **without custom code per test**, and switch a test off without a deploy.
- **GrowthBook Cloud (Starter) = assignment only.** It decides which variant a visitor gets (rules live in the GrowthBook UI, project `clearcutoff`, SDK connection `sdk_19g6dmwkflald`, environment `production` only).
- **Amplitude = events and results.** GrowthBook cannot read Amplitude without a data warehouse, so we never use GrowthBook's stats engine. Every analysis is an Amplitude funnel/chart broken down by the exposure user property (10A.6).
- **Do not confuse with Amplitude flags.** `practice_test`, `hard_gate`, `soft_gate`, `autopay-offer-99` are Amplitude flags read through `lib/experiments/experimentFlag.ts` (`getFlagVariant`). They were left untouched. New A/B experiments with a variant split use GrowthBook (this section); `practice_test` still switches the whole Practice Test on/off and is independent of the GrowthBook flag `dash_all_practice_skip_202611`.
- **Starter limits that shape the design:** 3 users, **1 project**, default environments only (so one environment, `production`), **1 webhook per SDK connection**, CDN 1M requests/month. Keep these in mind before proposing "a staging environment" or "a second project".

### 10A.2 Architecture (do not re-invent any of these pieces)
| Piece | Where | Role |
|---|---|---|
| `@clearcut/experiments` | `packages/experiments` (source-only, subpath exports `./id ./attributes ./exposure ./client ./react ./payload ./webhook`, no barrel, no Tailwind) | Framework-agnostic core. Depends on `@growthbook/growthbook` 2.1.0. |
| `id` | `cc_exp_id` | Sticky browser id GrowthBook hashes on (attribute `id`). Cookie (1 year, `Path=/`, `SameSite=Lax`, `Domain=.clearcutoff.in` on production hosts, `Secure` on https) mirrored in localStorage, so the variant survives landing -> OTP signup -> dashboard. Deliberately NOT Amplitude's deviceId (landing's Amplitude loads late; forcing an id would re-identify existing users). |
| `attributes` | `ExperimentAttributes` | `id`, `user_id`, `exam`, `utm_source`, `utm_campaign`, `locale`, `platform`, `is_logged_in`, `is_paid`, `plan_type`. `cleanAttributes` drops empty values so `"undefined"` never reaches a rule. |
| `exposure` | `createTrackingCallback` | When GrowthBook puts a visitor into an **experiment rule**, sends Amplitude `$exposure { flag_key, variant }` once per experiment+variant per page and sets user property `exp_<flag_key>` = variant key. Never throws. |
| `client` | `resolveConfig`, `createExperimentsClient` | `resolveConfig` returns `null` (= experiments OFF, everyone gets control, nothing fetched) when no client key **or** the host is not a production analytics host (`analyticsAllowedHere()` from `@clearcut/utils/analytics-hosts`; localStorage `cc-analytics-local=1` opts a local run in). With a server payload the client uses `initSync` (no request, no wait); without one it falls back to `init({ timeout: 500 })`, then control. Wrong type or any error returns control. |
| `payload` | `fetchFeaturesPayload` | **Server-side** fetch of `<host>/api/features/<clientKey>`, Next data cache `revalidate: 300` (the client's 5 minute rule) and tag `growthbook`, 1.5 s timeout, 30 s failure cooldown per server instance. Never throws; any failure returns `null`. |
| `webhook` | `verifyWebhookSignature` | WebCrypto, constant-time compare, 5 minute replay window, never throws. |
| `react` | `createExperimentsHooks({ getClient, configured })` | Returns `useExperimentValue(flagKey, control, enabled?) -> { value, ready }` and `ExperimentText`. **No provider**: the SDK is only loaded on pages that mount an experiment element. |
| App glue | `apps/dashboard/src/lib/experiments.ts` (+ `experiment-user.ts`), `apps/landing/src/lib/experiments.ts` | Lazy singleton client, wires Amplitude through the app's own helpers (`trackReservedEvent`, `setAnalyticsUserProperty` in dashboard `lib/analytics/browser.ts`). Dashboard's `AnalyticsProvider` calls `setExperimentUser({ user_id, is_logged_in: true })`. Each app exports its own `useExperimentValue` / `ExperimentText`. |
| Dashboard payload | `components/features/experiments/ExperimentsPayload.tsx` (server) + `ExperimentsBootstrap.tsx` (client) | Mounted **once in `app/[locale]/layout.tsx`**: every dashboard route already gets the payload, so a new dashboard experiment needs **no extra wiring**. Renders nothing without a key or a usable answer. |
| Webhook route | `POST /api/growthbook-webhook` | Expires the cached payload so a flag change or kill switch reaches visitors in seconds (10A.7). |
| QA page | `/growthbook-test` (dashboard, `(public-pages)`) | Practice surface for the real flag `dash_all_test_card_202611` + a debug panel. 404 in production unless `NEXT_PUBLIC_ENABLE_GROWTHBOOK_TEST=true`. |

Data flow in one line: GrowthBook CDN -> (server, cached 5 min, tag `growthbook`) `ExperimentsPayload` -> `ExperimentsBootstrap.setServerPayload` -> browser `initSync` -> `useExperimentValue` -> `$exposure` to Amplitude. Visitors never call GrowthBook themselves when the payload exists.

### 10A.3 Speed and UX requirements (non-negotiable, these are why the design looks like this)
- **No flicker, ever.** A visitor must never see control and then the variant. Use `useExperimentValue` / `ExperimentText`; never render the old UI while `ready` is `false` and swap later. While unknown, keep the **space** but hide it (`invisible` / `visibility:hidden`), never remove it (no layout shift). The answer is normally immediate (server payload), at most 500 ms on the browser path.
- **Never swap after settling.** If the features arrive too late, the visitor keeps control for that page view.
- **Every failure path = control.** No key, not a production host, GrowthBook down, bad payload, flag missing/off, wrong value type, unknown value, empty string: the page must equal today's behaviour. Write the variant check as "only the explicit variant value changes anything" (example: `allowSkipFromValue(value)` is `value !== "no_skip"`).
- **First view must be right.** That is why the payload is fetched on the server and handed to the browser; do not move a dashboard experiment back to the browser-fetch path.
- **Do not slow other pages.** The payload fetch runs in the layout of every dashboard route: keep the 1.5 s timeout and the 30 s failure cooldown; never `await` GrowthBook anywhere else on a request path; never add the SDK to a bundle that has no experiment element (keep the lazy singleton).
- **Copy tests:** `ExperimentText` accepts plain text, trimmed, max 60 chars, otherwise control. For anything else use `useExperimentValue` with a String/Boolean flag and render your own variants.
- LCP/CLS before/after on a production build has **not** been measured yet (phase 118 open item): if you change the loading path, measure it.

### 10A.4 When to use a flag / experiment, and when not
Use a GrowthBook experiment when: a product question has two or more concrete variants of copy, layout or flow, learners can be split by `user_id` (logged in) or `id` (anonymous, landing), and the outcome is an event Amplitude already records.
Do **not**: (a) use it as a permanent config store, (b) test anything money-related without a server-side check (the backend trusts browser prices, see the flagged item in §10; any pricing experiment needs that fixed first), (c) experiment inside the exam attempt/submit path or anything that must be identical for every learner (scoring, access, entitlement: those belong to the backend), (d) start an experiment yourself (10A.8), (e) migrate an existing Amplitude-flag test unless asked, (f) put an experiment on Astro `/go` (out of scope until its own phase; landing and dashboard only).

### 10A.5 Naming and flag shape
- Flag key: `<surface>_<exam|all>_<what>_<yyyymm>`, lowercase, e.g. `dash_all_practice_skip_202611`, `dash_all_test_card_202611`, `lp_all_cta_copy_202611`. Surfaces in use: `dash`, `lp`.
- Type **String** with an explicit control as the default value, e.g. `skip` (control) / `no_skip`. Keep control = today's behaviour exactly.
- Tracking key = the flag key. Experiment rule hash attribute: `user_id` for logged-in dashboard tests (same learner, same variant on every device and re-ask), `id` for anonymous landing tests. Rule: split 50/50 unless the client says otherwise; 100% of units for a full test.
- The control value and flag key live in a tiny pure file next to the feature (example `practice-test/practiceSkipValue.ts` with a unit test) and a hook (`usePracticeSkip.ts`); components never repeat the string literals.
- One experiment per surface per exam at a time; the behaviour of two experiments on the same page is untested.

### 10A.6 Targeting and measurement rules
- **Never put a phone number, email or name in a GrowthBook rule or attribute.** The rules are served from a **public CDN URL** anyone can open with the client key (verified on our own payload). Target by `user_id` (= `users.uuid`) or non-personal attributes only. To pick a test learner get the uuid with `SELECT phone, uuid FROM users WHERE phone IN (...)` (production DB: run by the user / backend owner, not by you).
- `user_id` is not in GrowthBook's default attribute dropdown: use the Advanced (JSON) condition, e.g. `{"user_id": "<uuid>"}`. The identifier `user_id` exists in SDK Configuration > Attributes.
- A **Force rule does not call the tracking callback**, so no `$exposure` is sent for it; only experiment rules do. Do not expect an exposure from a QA Force rule.
- **Reading the result:** Amplitude. Denominator = `$exposure` with `flag_key` = the flag. Break any funnel/chart down by the user property `exp_<flag_key>` (variant key: control rule value `0`, first variant `1`, as GrowthBook reports it). Numerators = **existing** events (`Test Started`, `Test Submitted`, `Payment …`). **Add no new event for an experiment**; add a property to an existing event only when unavoidable (rule in §2.5 and the analytics feedback: reuse, Title Case).
- Filter the analysis on exposure: learners who were already in the flow before the start get assigned at their next exposure point.
- Do not run `$exposure` on page load for something that is closed (see 10A.9).

### 10A.8 Who does what (process for a new experiment)
1. Phase doc first (`docs/phases/_TEMPLATE.md`, new number), with the client decisions listed as open until answered (copy, hidden controls, start date, stop rule/guardrails).
2. Code on a dedicated branch from main: pure value file + unit test, hook, component change, en/hi/mr copy if any text varies, nothing else.
3. In GrowthBook create the flag with **production OFF** and the experiment rule as an **unpublished draft**. **The client/user starts it** (publish the draft, then switch production ON); you do not start an experiment or switch a production flag on unless explicitly told.
4. Merge/push to `main` only on the user's explicit go-ahead.
5. Report what was NOT verified (real traffic, Amplitude UI, real device, hi/mr wording) in the phase doc.
GrowthBook UI work is done through the browser with the user logged in; anything you cannot do is reported, not worked around.

### 10A.9 Implementation do's and don'ts
**Do**
- Reuse `useExperimentValue` from `@/lib/experiments` (dashboard) or `apps/landing/src/lib/experiments.ts`; a new component needs no provider.
- **Components that are mounted while closed (sheets, modals, drawers):** read the flag in a child that exists **only while open** (example `PromptContent` inside `PracticeTestPromptSheet`). Reading in the always-mounted shell sends `$exposure` for everyone who merely loads the page and ruins the denominator. There is no silent flag read: GrowthBook marks any evaluation as tracked, and a later real exposure would be lost. So read where the learner actually sees it.
- Key the experiment component by `user.uuid` for `user_id`-targeted dashboard tests (`AuthProvider` renders a cached user first, then confirms 2-4 s later; without the key another login on the same browser got the previous user's variant).
- Keep the **layout** of the varying control until the answer is known (`invisible`), so nothing moves afterwards.
- Keep a way out for the learner in every variant (example: the Practice Test error screen keeps "Go to Preparation" even in `no_skip`).
- Test with the real SDK and stubbed HTTP in `packages/experiments` (`pnpm --filter @clearcut/experiments test`), unit-test the pure value file, then check in a real browser: flag absent = control, variant, flag switched OFF (webhook), GrowthBook returning 500, hi + mr at 390 px, double taps, one `$exposure` per page view, 0 browser requests to GrowthBook.
- Verify like the rest of the repo (§8, §8.1): typecheck vs the baseline, eslint, `pnpm check:colors`, and say "Not verified:" for what was not run.

**Don't**
- Don't import `@growthbook/growthbook` in an app directly; go through `@clearcut/experiments`.
- Don't create a second client, a provider, a barrel file, or a copy of the package logic in an app.
- Don't hardcode a variant, a flag key string in several files, or `process.env.NEXT_PUBLIC_GROWTHBOOK_*` outside the app's `lib/experiments.ts` and `ExperimentsPayload` (literal reads are required so Next inlines them).
- Don't render control, then variant. Don't remove the element while loading. Don't add a loading spinner for it.
- Don't put personal data in rules, don't add `NEXT_PUBLIC_` to the webhook secret, don't commit keys.
- Don't relax the webhook (no unsigned accepts, no parsing the body, no logging the secret).
- Don't change existing flags/experiments (`dash_all_test_card_202611`, `dash_all_practice_skip_202611`, `lp_all_cta_copy_202611`) or published GrowthBook revisions unless asked. `lp_all_cta_copy_202611` is still live in GrowthBook but nothing reads it.
- Don't test or start experiments against production real learners without the user.

- **Meta Pixel (dashboard + landing `FacebookPixel.tsx`, `@clearcut/auth/facebook-pixel`, `lib/analytics/facebook-pixel.ts`)**:
  - The pixel loads on page load, not on first interaction (client requirement). Gate effects on `scriptReady`, set from `Script`'s **`onReady`**. `onLoad` is never called for an inline `<Script>` in next/script, so using it leaves the flag `false` and silently kills every effect-driven event.
  - Never block an event on the geo lookup. `getMetaGeoData()` has one total budget (1.5s) and caches per session; use `readCachedMetaGeoData()` where waiting is not acceptable (PageView).
  - An event fired right before a **hard** navigation (`window.location.href = …`) must be `await`ed, or the page tears down before `fbq('track')` runs. SPA `router.push` is safe.
  - **Where the pixel may load (CC-115):** only the production hosts in `META_PIXEL_HOSTS` (`packages/utils/src/meta-pixel-env.ts`, same list in ASTRO `packages/auth/src/lib/facebook-pixel.ts`). Every other host (localhost, maintest, previews) is off unless the browser opted in. Use `metaPixelId()`; never load fbevents.js directly.
  - **Ad click id (CC-130):** each pixel component calls `persistFbcFromUrl()` (`@clearcut/utils/meta-fbc`) on mount; it writes `_fbc` on `.clearcutoff.in` so Purchase on app.clearcutoff.in carries fbc. ASTRO `/go` loads the pixel on page load too (it waited for the first interaction before 2026-10-23).
  - **Purchase value comes from the backend** (`meta_purchase.value`, BE `MetaPurchaseService`: ex-GST, minus Razorpay fee, × plan multiplier). Don't compute a Purchase value in the browser.
  - PageView is per route (ref keyed on `pathname`), not per query change, so one-shot params stripped with `router.replace` don't send it twice. Don't add an inline `fbq('track','PageView')` to the script body as well.
  - **Re-calling `fbq('init', PIXEL_ID, {...})` (or `fbq('set','userData',...)`) after the pixel's first `track()` has already fired does NOT attach new advanced-matching fields — confirmed 2026-10-08 via live network inspection (direct `/tr` request payloads) against the real production pixel, and independently corroborated by Meta's own Advanced Matching docs ("place advanced matching parameters in the pixel base code") and developer-community reports (incl. a quote from Simo Ahava) describing the same `fbevents.js` limitation.** Precisely: a key is only ever read from the FIRST `init()` call for a given pixel ID on the page — a later `init()`/`set()` call can update the *value* of a key that was already present in that first call (e.g. `country`), but can never add a brand-new key (`ph`, `external_id`, `ct`, `st`, `zp`), no matter whether it's called before or after the first `track()`. This means the "re-init before track" pattern used throughout this codebase (`trackFacebookLead` in `packages/auth/src/facebook-pixel.ts`, `trackFacebookEventWithUserData`/`setMetaUserData` in dashboard) only ever worked for `country` — phone/external_id/geo never actually reached Meta on any event that fires after PageView (i.e. almost all of them, since PageView always fires first). **The fix**: bake whatever's already cached (`auth_user_cache` for phone/id, `meta_geo_data` for geo — both read synchronously, in plain JS, inside the inline bootstrap `<script>`, before fbevents.js or React even run) into that one first `init()` call — see `apps/dashboard/src/components/thirdparties/FacebookPixel.tsx` and `apps/landing/src/components/thirdparties/FacebookPixel.tsx`. Because matching data persists for the pixel's whole lifetime once set, this one fix covers every later event too (Lead, Purchase, InitiateCheckout, …) for any visitor who already had cached data at page load — it does NOT help a visitor who authenticates mid-session without a subsequent full page load, since nothing can add a new key after the fact short of either delaying the first track() (rejected — PageView must fire immediately) or manually constructing/self-hashing a raw `<img>`-style request straight to `facebook.com/tr` per event (Meta's own documented workaround for this exact SPA case) — this deliberately wasn't built; flagged as the real follow-up if 100% coverage on new-user-logs-in-mid-session events is required. **Never pass a placeholder/fake value for an unavailable field just to "reserve" the key** — sending fabricated PII to Meta is worse than sending none.
